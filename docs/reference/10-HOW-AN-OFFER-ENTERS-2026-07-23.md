# How an offer enters the system

> Written on 23 July 2026. Everything here is verified against the code, against the
> real Notion schema and against PROD. What could not be verified is marked as such.

## The rule that overrides all others

**The CV is written by the prompt. Never by Claude by hand in the chat.**

On 23 July the recruitment-agency CV was generated by correcting by hand, in the
conversation, each failure as it appeared. A good CV came out and the system stayed
just as broken: the prompt learned nothing, and the next offer would have let PHP slip
in again and added leadership verbs.

When the generated CV has a flaw, the fix goes in **the cv-server prompt**, not in the
CV. Correcting the result by hand hides the problem and guarantees it will repeat.

Claude's role in a direct-contact offer is to put it into Notion. Nothing more.

## The three ways an offer enters

| | From where | Who brings it | Writes to |
|---|---|---|---|
| 1 | Tecnoempleo, Adzuna, Remotive, Indeed | n8n, scheduled workflows | Ofertas de Trabajo |
| 2 | LinkedIn | Claude cowork scheduled task | Ofertas de Trabajo |
| 3 | LinkedIn or email, they write to you | Verónica, telling Claude | Ofertas de Trabajo |

Paths 1 and 2 produce the same thing: **a detected offer**, which may not be of
interest. Path 3 does not: when someone writes to you, the decision that it is of
interest has already been made.

## The origin is not a status

When a direct-contact offer comes in, the temptation is to add a new status, "They
contacted me", at the start of the cycle. **It does not work.**

`Estado` (status) answers *where is this now*. The origin answers *how did this
arrive*. The status changes constantly; the origin never changes. Putting the origin
inside the status loses the data as soon as the application moves forward: by the time
it reaches `Entrevista` nobody remembers that they came looking for you.

And that data is valuable. "Of everything that reaches me, how much comes without my
looking for it" is the measure of whether the LinkedIn profile and the CV are working.
If it lives in `Estado`, the question cannot be answered.

If it is to be recorded, it goes in a property of its own. Not in `Estado`.

## A direct-contact offer enters at the end

The normal route is: the bot searches, filters, notifies by email, you wait, you
approve, CV and cover letter are generated.

When they contact you, the first four steps do not exist. There is nothing to search
for or decide. So there is no need for a status *before* `Pendiente`: what is needed is
to be able to create the card **already in `Aprobado`**, which is what triggers the
generation of the CV and cover letter.

## The two Notion databases, and which one serves what

| | **Ofertas de Trabajo** | **Candidaturas · Control de CVs** |
|---|---|---|
| Data source | `collection://<id>` | `collection://<id>` |
| Who writes | n8n and the Claude task | Only Verónica |
| Statuses | 9 | 5 |
| Has `Descripción` | Yes | **No** |
| Has `Idioma` | Yes | **No** |
| Has `Vía / Recruiter` | No | Yes |

**Offers always go to `Ofertas de Trabajo`.** It is not a preference: `Candidaturas`
has neither `Descripción` nor `Idioma`, and without those two fields a tailored CV
cannot be generated, because the offer description is exactly what the cv-server reads.

`Candidaturas` is a summary table, not a case file.

The two status vocabularies do not match (`Oferta recibida` versus `Oferta`), and that
remains unresolved.

The column mixes two life cycles in a single property: that of the automation and that
of the real application. That is why none of the statuses fits well for an offer that
enters by hand.

## Where an application lives today

Spread across four places, with no link between them:

| What | Where |
|---|---|
| The offer and its status | Notion, Ofertas de Trabajo |
| The tailored CV | Google Drive, folder `FOLDER_CV_GENERADOS` |
| Interview preparation | `buscartrabajo/entrevistas/`, inside git |
| The follow-up | In Verónica's head |

`entrevistas/<company>-prep/` contains a complete backend challenge, with code, study
notes and questions and answers. It is a live application stored in a git repository
and disconnected from Notion.

**Undecided:** where the follow-up of an application lives once there is an interview.

## The two repositories

| | `buscartrabajo` | `cv-server` |
|---|---|---|
| Remote | `github.com/cookyourweb/buscartrabajo` | `github.com/cookyourweb/cv-server` |
| What it contains | Documentation, n8n exports, scripts | The Flask application, split into modules (`server.py`, `llm.py`, `guardrails.py`, `notion.py`, `drive.py`, `docx_render.py`) |
| Code that runs | None | Yes, on Render |

They are two independent repositories. The `sistema-buscartrabajo` folder that contains
them is **not versioned by either one**. There is no common place.

Consequence: whoever clones `cv-server` sees nothing of `buscartrabajo`, and vice
versa. The description of the system has to live in a single repository and the other
one points to it by URL, never copying it. Duplicating the truth is what produced the
eleven contradictions in document 08.

## Where the program really lives

In n8n, in the cloud, **outside git**. There is no file that can be opened to read what
the system does every morning.

This explains why the documentation of this project keeps going stale: the system can
be changed entirely without leaving a trace in any commit. An export saved in
`workflows/` is a snapshot of the day it was exported, not the system.

**Before stating anything operational, verify it against the live source.** The repo
cannot contradict Verónica about what is in n8n.

## Traps verified on 23 July 2026

Snapshot of that date. Since then `cv_server_railway.py` was split into modules
(`server.py`, `llm.py`, `notion.py` and others), so the code references are by module
and not by line. Verify each entry against the current code before relying on it.

- **`cv-server/real_jobs.py` is switched off.** It is 465 lines for searching offers,
  but it only implements Remotive and nobody calls it: the PROD workflow searches on its
  own. Whoever opens it thinking it is the system's searcher is reading dead code. Same
  for the `/buscar-ofertas-reales` endpoint (in `server.py`).
- **`/health` lies about the LLM.** It returns `llm_provider: groq` and
  `version: v2.3-groq`. CVs are written by `claude-haiku-4-5` (`CV_MODEL`, in `llm.py`)
  and cover letters by `claude-sonnet-4-6` (`CARTA_MODEL`, in `llm.py`). Since then
  `/health` reports the real models and in production the CV is also written by
  `claude-sonnet-4-6`. It is the same pattern as the `modelo_usado` bug fixed on 22
  July: reporting a constant instead of what happens. It is contradiction 12, and it is
  not in the audit of document 08.
- **`api.py` is not deployed.** It is the migration to FastAPI, with green tests, but
  the `Procfile` still starts Flask with gunicorn.
- **`.claude/INSTRUCCIONES-INICIO.md` is stale** since 21 April. It says to read a
  `CLAUDE.md` that does not exist, to call the n8n instance `n8n-qwmu` which is
  deprecated, and to `cd` into a path that no longer exists. Of its steps marked as
  mandatory before touching anything, half fail when run.
- **`POST /crear-oferta` returns 404.** The Notion module (`notion.py`, formerly
  `cv_server_railway.py`) used the data source id where page creation needs the database
  id. For path 3 it does not need fixing: Claude creates the card directly against
  Notion.
