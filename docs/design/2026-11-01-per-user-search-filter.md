# Per-user search filter

**Date:** 1 Nov 2026 · **Status:** Phase 1 deprecated (fallback only). Phase 2 (spec 009) is live in production.
upload to n8n pending (`workflows/PROD/IGVSEBCp1sFMXYYB-2026-11-01-filtro-por-usuario.json`,
generated by `scripts/patch_filtro_por_usuario_2026_11_01.py`).

Real offers of 29-31 Oct, filtered by Groq with the new prompt:

| Profile | Before | After |
|---|---|---|

## The problem

From 29 Oct to 1 Nov no new offer entered Notion. n8n was not down: the daily run at
09:00 finished as `success` every day. It found almost nothing, and what it found it
discarded. Four causes, verified in the executions of workflow `IGVSEBCp1sFMXYYB`:

1. **Adzuna returns 503 every day since at least 25 Oct.** The source is lost.
2. **The other sources are thin.** Remotive brings 10-12 jobs, Tecnoempleo a short RSS.
3. **The Groq filter is written for one person.** Its prompt says "Veronica works from
   Madrid", hardcodes a 60,000 EUR floor and 400/day, accepts remote only from "Spain,
   Europe, EMEA or worldwide", and discards any hybrid outside Madrid.
4. **More hardcoded criteria outside the prompt.** The title prefilter in `Formatear
   ofertas` always excludes `java`, `golang`, `devops` and `backend`, which suits the
   owner and nobody else. `Code - Normalizar Modalidad`, after Groq, discards every
   on-site offer and every hybrid one outside Madrid. Angular offers were lost in Groq
   because Angular was not in the owner's stack.
5. **The Groq seniority rule demanded "Senior" in the title.** Spanish offers rarely
   write it. The prefilter had already been fixed for this on 28 Aug; Groq had not.

Points 3 and 4 are not a configuration slip: they mean the filter is **not
multi-user**. A second user in Valencia with a 45K floor would be judged with the
owner's criteria. Fixing it only for the owner would bring the problem back with the
next user.

## The rule this design follows

**A user configures their search in their own profile. Nothing about a user lives in
the workflow.** The owner becomes one more user.

## What is hardcoded today, and where it comes from after

| Today, in the prompt or the code | After |
|---|---|
| "Veronica" | `nombre` from the profile |
| "works from Madrid" | `ciudad` from the profile |
| Floor 60,000 EUR | `salario` from the profile (already passed to the prompt, but ignored by the hard filter) |
| Freelance floor 400/day or 50/hour | Derived: `salario / 150` per day, `salario / 1200` per hour |
| Remote valid only from Spain, Europe, EMEA, worldwide | "Remote must accept the user's country or region, inferred from `ciudad`" |
| Hybrid valid only in Madrid | Hybrid valid in every city listed in `modalidad` as `Híbrido <city>` |
| `Evitar` | Not read today. Becomes a hard filter |
| Stack prefilter drops non-matching offers | Prefilter only removes offers with **zero** overlap and no AI keyword; the AI judges the rest from the description |

## The occasional-hybrid city

The owner accepts hybrid in Barcelona if it is about one office day a week or less. The
general form: **a hybrid city in `modalidad` that is not the user's `ciudad` is
"occasional".** The filter lets those offers pass and starts `notas` with
`HIBRIDO <CITY>: confirmar días de oficina`. Nothing is discarded for being far if the
user said they accept that city.

## Where the preferences live

ADR-005 says Notion is frozen on migration day and Postgres (`perfil`, via `cv-server`)
becomes the only truth. Today n8n still reads users from Notion. This design does not
add a second place to write the same thing:

**Phase 1, now, no schema change.** The prompt and the two Code nodes read only fields
that already exist in the Notion `Users` database: `Name`, `Ciudad`, `Salario min`,
`Modalidad` (whose options already include `Híbrido BCN`), `Stack`, `Perfil`, `Rol
objetivo` and `Evitar`. Updating the owner's values (adding Angular and Next.js to
`Stack`, `Híbrido BCN` to `Modalidad`) is data entry, which ADR-005 allows before
migration.

**Phase 2 is the SDD change `ofertas-por-usuaria`, already accepted on 21 Oct** (engram
`sdd/ofertas-por-usuaria/*`: explore and proposal done, specs pending). It moves the
search to `cv-server`, one user per call, reading the profile from Postgres; n8n only
triggers it. This design does not open a parallel path. It hands that change two
inputs for its spec:

- the filter rules of Phase 1, already written per user, so they move to `cv-server`
  as they are;
- the profile fields that Phase 1 has to infer and Postgres should store explicitly:
  `regiones_remoto text[]`, `ciudades_hibrido text[]`, `tarifa_dia_min integer` and
  `evitar text`. Today `perfil` has `stack`, `modalidad` (remoto, hibrido, presencial),
  `ubicacion` and `salario_min`, but no hybrid cities, regions or exclusions.

Phase 1 is a stop-gap so the owner gets offers again while that change is built. It is
thrown away when `ofertas-por-usuaria` ships.

## Changes in Phase 1

All in workflow `IGVSEBCp1sFMXYYB`. Backup taken before any change:
`workflows/PROD/backups/IGVSEBCp1sFMXYYB-2026-11-01-antes-filtro.json`.

1. **`Code — Normalizar users (schedule)`**: also pass `evitar` (`Evitar` rich text).
   The internal and webhook normalisers, if present, get the same field.
2. **`Formatear ofertas`**: loosen the stack prefilter as described above.
3. **`Groq - Generar Ofertas`**: rewrite the hard filters with every user value taken
   from `$json`. Rule 3 becomes:
   - discard on-site outside the user's `ciudad`;
   - hybrid: pass if the city is the user's `ciudad` or any `Híbrido <city>` in
     `modalidad`; mark occasional cities as above; discard other cities;
   - remote: pass unless restricted to a region that excludes the user's country;
   - discard anything that matches `evitar`;
   - a pure frontend role is as valid as an AI or full-stack one.
   Ordering stays: AI first, then fit, salary, remote before hybrid.

Not in this change: Remotive domain, Adzuna 503, a per-user Tecnoempleo feed and Google
Jobs. They come next, in that order. Google Jobs and Tecnoempleo must search per user
from the same profile fields, never with a fixed query.

## Adzuna and Google Jobs (added 1 Nov 2026)

Adzuna answers 200 to the exact n8n query from a local machine, with the same key, and a
generic nginx 503 to n8n on Render every day since about 25 Oct. Malformed requests give
400 or 401, never 503. The most likely cause is a block on Render's datacenter IPs. A
support message was drafted for the owner to send.

Google Jobs (SerpApi `google_jobs`) is added as a per-user source, between Tecnoempleo
and `Formatear ofertas`, generated by `scripts/patch_google_jobs_2026_11_01.py`:

- **Query per user:** the first role of `Rol objetivo`, `location` = the last part of
  `ciudad` + ", Spain" (v1 scope of `ofertas-por-usuaria`), `hl=es`, `gl=es`.
- **Budget:** one search per active user per day. The free plan has 250 searches a month,
  50 per hour, so it covers about 8 users. Each search returns up to 10 jobs.
- **Key:** an n8n "Query Auth" credential (`api_key`) the owner creates in the UI. Never
  in the workflow JSON or the repo.
- **Failure:** `onError: continueRegularOutput`, like the other sources. A failed search
  does not stop the run.
- **Parsing:** same `matchea`, dedup and region checks as the other sources. The link is
  `apply_options[0].link`, falling back to `share_link`. `work_from_home` maps to "Remoto".

**Result of the live test, 1 Nov 2026: NOT deployed.** SerpApi works (key valid, Free
Plan) and `google_jobs` returns 10 jobs for New York and for London, but **0 for Spain**
in five variants: `hl/gl=es` with `location` "Madrid, Spain" and with SerpApi's canonical
"Madrid,Community of Madrid,Spain", `google_domain=google.es`, query "AI Engineer Madrid"
in English, and a Spanish query with no location ("desarrollador frontend"). Google
returns "Google hasn't returned any results for this query". The patch and its output
JSON stay in the repo, unused, in case remote UK roles become a target. Seven of the 250
monthly searches were spent on the test.

**Second test, same day: remote Europe from the UK. Adopted.** Berlin, Amsterdam and
Lisbon also return 0 (Dublin: `ie` is not a valid `gl`), so Google Jobs gives nothing
for EU countries through SerpApi. A UK search for "AI Engineer remote Europe" returns 10
jobs, 9 of them remote and open to Europe or anywhere (ElevenLabs, Axelera AI,
Copperleaf…). The node now searches `<first role> remote Europe` with `gl=uk`,
`location=London`. Spain itself stays covered by Tecnoempleo and LinkedIn. Replay
through `Formatear ofertas` and Groq with the owner's profile: 10 pass the prefilter,
5 pass Groq (the junior and UK-only ones are dropped).

## How we know it works

- **Replay**: run the filter prompt offline against the stored offers of 29, 30 and 31
  Oct (in the execution data) for the owner's profile. Expected: the Angular and the
  Barcelona-hybrid offers that were discarded now pass, marked where needed.
- **Second profile**: the same replay with a fake profile (Valencia, 45K, remote only,
  `Evitar: Java`). Expected: different results, no mention of Madrid or 60K.
- **Next real run** at 09:00: duration back near 100 s and offers in Notion.

## Rollback

Re-import the backup JSON in n8n and activate it. The Notion data changes are additive
and can stay.
